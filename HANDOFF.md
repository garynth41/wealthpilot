## Runbooks (0.25.0 – 0.25.1)

**Database tests without staging (0.25.1).** `npm run db:test` applies every migration to an empty local Postgres with a small Supabase stand-in (`supabase/tests/stub.sql`), the newest twice, then runs `supabase/tests/*.test.sql` (each check prints PASS or stops with FAIL). CI's `database` job does the same on every push; locally it needs psql and a server (`docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres postgres:16`, then `PGHOST=localhost PGUSER=postgres PGPASSWORD=postgres npm run db:test`). The stand-in is not Supabase (postgres is a superuser there, and the sign-in and storage services add checks of their own), so staging stays the real test.

**Every database change: staging first.** `node scripts/staging-schema.mjs --from NNNN > /tmp/s.sql`, apply it to `wealthpilot-staging` (`leivqwnstptwoqwuuglh`), let CI's `staging` job pass, then apply the migration file to production (`dshswfcpovdpxcidolqb`) and run `get_advisors`. To run the staging tests by hand: build with `VITE_SUPABASE_URL=$STAGING_URL VITE_SUPABASE_KEY=$STAGING_KEY npx vite build --outDir dist-staging`, then `npm run e2e:db` with the three `STAGING_*` variables set.

**Staging test users** (set up 2026-11-06): `e2e-owner@wealthpilot.test` and `e2e-viewer@wealthpilot.test`, password in the GitHub secret `STAGING_E2E_PASSWORD` only. They were created from bcrypt hashes through a one-time function that worked only while no test user existed and was dropped straight after; `supabase/staging/e2e.sql` does the same from the SQL editor (paste the two hashes). To change the password: new hashes → `update auth.users set encrypted_password = '<hash>' where email like 'e2e-%@wealthpilot.test'` on staging, then update the secret.

**Rotating the scheduled jobs' secret** (once a year, or at once if it may have leaked). In the Supabase SQL editor (production):
1. `select public.rotate_cron_secret();` — a new random value replaces the old one in Vault. The jobs read it at run time and the functions check it against Vault, so nothing else changes. The value is never shown.
2. `select public.cron_ping();` — note the number it returns, wait a few seconds, then `select status_code, content from net._http_response where id = <that number>;` → `200 {"ok":true,…}`.
3. `select * from public.cron_status();` the next morning — every job's last run should be `succeeded`.
If a `CRON_SECRET` function secret was ever set on an edge function, delete it (Project → Edge Functions → Secrets): the functions accept it as well as the Vault value, so it would survive a rotation.

## Architecture in one minute

`pages/*` render from the zustand store (`app/store.ts`) which holds the whole household in memory (`Data`) and writes through a `Repo` (`SupabaseRepo` or `MemoryRepo` for the offline demo/tests). Realtime changes trigger a debounced `refresh()`. All math lives in pure functions under `lib/` (unit-tested) — pages only format. Email capture: `lib/email/extract.ts` (email → fact, never invents numbers) → `propose.ts` (match to accounts / recurring / categories, describe changes) → `apply.ts` (writes). Charts go through `components/Chart.tsx` (readable-layout rules from CareerShift v1.26).

## Data model (19 tables)

households, household_members, household_invites · accounts (assets and liabilities in one table, `kind` decides) · statements · categories (group, priority Essential/Important/Discretionary, Fixed/Variable/Irregular, default_budget, rollover) · pay_schedules (frequency + anchor date) · budget_periods + budget_lines (plan only; actuals derived) · transactions (positive amount; kind expense/income/transfer; transfer to a liability = debt payment) · recurring + bill_occurrences · goals + goal_contributions · planned_items · net_worth_snapshots · hardship_outreach · holdings (0.6.0) · email_items + email_ledger · activity_log, ref_counters, app_meta.

## Conventions to keep

- Edit engines in `src/lib`, not in pages. Add a unit test in `src/lib/engines.test.ts` or `src/lib/email/email.test.ts` for every rule change.
- Run `npm run check` before delivering; keep `README.md` current; bump `APP_VERSION` in `src/app/config.ts` (and `app_meta.latest_version` in the DB) on each release.
- Never store email bodies or more than the last 4 digits of an account. Never invent an amount or date that is not in the email.
- Schema changes: add a new file under `supabase/migrations/` AND apply it with the Supabase MCP (`apply_migration`); then run `get_advisors` (security).
